# 任务拆分与排期（v2.3）

> 单人开发，核心 v1 预计 10~14 个工作日。主架构为同一台腾讯云轻量应用服务器上的 Nginx + React/Vite + Hono.js/Node.js API + Drizzle ORM + PostgreSQL，使用 Docker Compose 管理服务。任务按纵向切片拆分，每个任务完成后都具备可演示或可验证的端到端行为。

当前运维前置状态：

- [x] 腾讯云服务器已配置 COS；
- [ ] 部署 Docker Compose 并完成 PostgreSQL 容器健康、连接和持久化验证；
- [ ] 验证通过后，接入每日 `pg_dump` → COS 自动备份。

| 03 | Excel 导入与失败恢复 | v1 | 01、02 | 2~3 天 |

## 01：Hono.js/Node.js 后端与数据库基础

**优先级**：P0

**交付**：初始化 Hono.js + Node.js + TypeScript 后端项目，配置 PostgreSQL 连接和 Drizzle ORM；完成 `drizzle-orm`、`drizzle-kit` 的 schema 与迁移流程，建立 `app_users`、`employee_work_batches`、`employee_work_items`、`pricing_batches`、`pricing_items` 数据结构、索引和约束。服务器和公网部署在任务 06 完成。

**验收标准**：

- Hono.js 后端可以在 Node.js 上启动，TypeScript 编译和依赖 lockfile 检查通过；
- PostgreSQL 连接配置通过环境变量提供，使用连接池和参数化查询，数据库连接失败时应用给出明确错误；
- `drizzle-orm` schema 与 PostgreSQL 表结构一致，`drizzle-kit` 可以生成并执行版本化迁移；
- 完成员工工作批次/明细、选品定价统计批次/明细和用户表的外键、检查约束、列表筛选索引和迁移脚本；
- `created_by`、`created_at`、`updated_at`、`batch_id` 等系统字段由 API 和数据库约束保护；
- 数据库密码、JWT 密钥和备份凭据通过环境变量或受限文件提供，不进入仓库和前端构建产物；
- 完成数据库连接、迁移和基础 schema 的自动化测试；
- 当前阶段不开放原始数据删除、字段编辑和批次回滚能力，相关能力留到后续版本。

## 02：认证、权限与 Hono API

**优先级**：P0

**阻塞于**：任务 01

**交付**：使用 Hono.js 在 Node.js 上提供健康检查、认证、权限和业务 API；完成邮箱密码登录、JWT 登录态、团队成员准入、角色权限中间件、统一错误处理和环境变量校验。前端通过 API 访问业务数据，不直接连接数据库。

**验收标准**：

- API 提供健康检查、登录、当前用户和退出接口，已开通成员可以登录并获得有效登录令牌；
- API 提供管理员注册接口，仅 `owner` 可以注册新的管理员账号，新账号立即启用且不会自动切换当前登录态；
- 密码使用安全哈希保存，接口不返回密码哈希，登录失败不泄露账号是否存在；
- 只有 `app_users.is_active = true` 的成员可以访问业务 API，未开通账号得到明确的无权限响应；
- API 从 JWT 确定当前用户，客户端伪造 `created_by`、角色或用户 ID 不会改变服务端身份；
- 只有 `owner` 可以调用员工工作导入接口，其他已登录成员只能查看员工工作记录；
- API 与数据库访问通过 service/repository 层和 Drizzle ORM 封装，前端页面不直接调用数据库驱动；
- 请求参数和响应结构使用 Zod 或等效 schema 校验，统一返回错误码、错误消息和 HTTP 状态码；
- 缺少或错误的环境变量、无效令牌、权限不足和数据库异常都有明确且不泄露敏感信息的错误响应；
- 后端测试覆盖登录、令牌失效、成员准入、角色权限和伪造身份字段；
- 后端测试或接口验收覆盖管理员注册的权限、重复邮箱、密码校验和角色固定行为；
- 本地开发环境可以重复验证登录、令牌失效和路由保护。

## 03：员工工作 Excel 导入与失败恢复

**优先级**：P0

**阻塞于**：任务 01、任务 02

**交付**：老板通过 Hono.js API 上传客服/员工提交的固定模板 Excel，填写实际员工和工作日期，可以看到解析、写入和结果进度；服务端记录上传账号并自动创建工作批次；导入失败可以定位并重试，重试不会重复写入已成功的数据。

**验收标准**：

- 支持 `.xlsx` 和 `.xls`，并对表头、空文件、商品名称、价格格式和 5 万行上限进行校验；
- Excel 文件上传到 Hono.js API 后由 Node.js 服务端解析和分块处理，浏览器不直接向数据库批量写入；
- 导入页面展示待处理行数、成功写入数、总行数和当前状态；
- 每次导入生成员工工作批次，包含员工姓名、工作日期、文件名、上传人、时间、总数和错误范围；
- 每行数据自动关联工作批次，客户端不能覆盖批次、员工和工作日期字段；
- 部分失败时保留失败范围和错误原因，支持从失败位置重试且不会产生重复数据；
- 真实腾讯云服务器环境下 5 万行导入在 2 分钟内完成，页面结果与批次结果一致；
- 导入接口测试覆盖文件类型、行数上限、权限不足、部分失败和重复重试场景。

## 04：员工工作明细查询与筛选

**优先级**：P0

**阻塞于**：任务 01、任务 02

**交付**：登录成员可以分页浏览员工工作明细，并按员工和工作日期筛选；列表展示 7 个 Excel 字段及员工、日期信息，适用于几十万行数据规模。

**验收标准**：

- 员工工作列表使用 API 服务端分页，每页 100 条，翻页不重复、不遗漏；
- 可以按员工和工作日期筛选，结果与批次字段一致；
- 列表展示序号、货号、平台、商品名称、链接、规格、价格、员工和工作日期；
- 50 万行数据下分页和员工/日期筛选使用索引，真实服务器环境 p95 响应时间小于 1 秒；
- 未登录或未开通账号不能通过 API 读取业务数据；
- 链接字段按普通文本展示，外部跳转行为不阻塞 v1 核心验收。

## 06：Docker Compose 部署与 PostgreSQL 验证

**优先级**：P0

**状态**：进行中（已开始准备部署基线，待腾讯云服务器实机验收）

**阻塞于**：任务 01、任务 02、任务 03、任务 04、任务 05

**交付**：将 React/Vite 构建产物、Hono.js/Node.js API 和 PostgreSQL 部署到同一台腾讯云轻量应用服务器，使用 Docker Compose 管理服务，Nginx 提供前端静态文件、反向代理和 HTTPS。本任务只完成部署基线和 PostgreSQL 验证，不启用 COS 定时备份。

**验收标准**：

- 腾讯云轻量服务器完成 Ubuntu、Docker、Docker Compose 和域名配置，Nginx、Hono.js/Node.js API、PostgreSQL 由 Compose 管理并可开机自启和异常重启；
- `docker compose ps` 显示 PostgreSQL 容器为 `healthy`，容器日志无反复重启、鉴权失败或数据目录异常；
- 可从 API 容器连接 PostgreSQL，并完成迁移、最小读写和 API 健康检查；
- PostgreSQL 挂载持久化数据卷，重启容器后测试数据仍存在；
- React/Vite 构建产物由服务器上的 Nginx 提供，通过正式 HTTPS 域名访问；Nginx 将 `/api` 请求转发到 Compose 内部的 Hono.js API；
- Nginx 配置 HTTPS 证书、自动续期和到期检查，前端与 API 的访问链路可验证；
- Hono.js API 和 PostgreSQL 只加入 Compose 内部网络，防火墙只开放 80、443 和受限制的 SSH 端口，数据库端口不对公网开放；
- 生产环境通过环境变量注入数据库连接、JWT 密钥、Cookie 签名密钥和第三方凭据，不暴露敏感管理密钥；
- Nginx 访问日志、错误日志、Hono.js 应用日志和 PostgreSQL 日志按天切分并保留，健康检查可以发现 API 或数据库异常；
- 记录 CPU、内存、磁盘和 5 万行导入期间的资源峰值，确认资源限制不会导致服务异常；
- 3 名团队成员同时完成登录、筛选和查看，无明显卡顿或数据串写；
- 核心路径“登录 → 导入员工数据 → 按员工/日期筛选”完整跑通，5 万行导入达到任务 03 的标准。

## 07：每日 `pg_dump` → COS 备份与恢复演练

**优先级**：P0

**阻塞于**：任务 06

**交付**：在任务 06 确认 PostgreSQL 容器健康、可连接且持久化有效后，接入每日 `pg_dump` → 腾讯云 COS 自动备份，完成保留策略、失败可观测性和恢复演练。

**验收标准**：

- 备份任务启动前检查 PostgreSQL 容器健康状态和数据库连接，检查失败时立即终止；
- 每日自动执行 `pg_dump`，备份文件名包含数据库名和 UTC 时间戳，避免对象覆盖；
- `pg_dump` 成功后将备份上传到已配置的 COS Bucket，并验证远程对象存在且大小非零；
- COS 凭据、Bucket、Region 和路径前缀只存于服务器环境变量或受限配置文件，不进入仓库、镜像或日志；
- `pg_dump` 失败、COS 上传失败和对象校验失败都返回非零状态并留下日志，不会误报成功；
- COS 保留最近 7~14 天备份，过期对象由 COS 生命周期或受控清理任务删除；
- 从 COS 下载一份备份，在隔离数据库中完成恢复，验证核心表、行数和 API 启动；
- 记录首次手动备份、首次定时备份和恢复演练的结果。

## 08：v1.1 扩展功能

**优先级**：P1

**阻塞于**：任务 03、任务 04、任务 05

**交付**：在 v1 稳定运行后，增加管理员和成员管理、商品查找、授权数据维护及批次回滚能力，同时保持 v1 的导入追溯和备注编辑行为不变。

**验收标准**：

- 管理员可以管理团队成员和角色，非管理员不能执行成员管理操作；
- 支持按平台筛选，以及按货号或商品名称模糊搜索；
- 上传人可以删除自己导入的商品，管理员可以按授权规则删除任意商品；
- 授权用户可以编辑货号、价格等商品字段，但系统字段仍受保护；
- 批次管理页可以查看导入历史，并执行可确认、可恢复的整批回滚；
- v1.1 不包含操作审计、修改历史和删除日志。

## 依赖关系

- 任务 01 是 Drizzle schema、数据库、认证、API、导入和列表查询的共同基础；
- 任务 02 必须在任务 01 完成数据库和服务器基线后开始；
- 任务 03 依赖任务 01 的 Drizzle schema/迁移，以及任务 02 的登录态和权限中间件；
- 任务 04 可以与任务 03 并行开发，但必须依赖任务 01 的索引和任务 02 的受保护 API；
- 任务 05 已完成，选品定价统计导入与员工工作记录保持独立批次和查询链路；
- 任务 06 必须等待当前员工工作记录核心链路完成；
- 任务 07 必须等待任务 06 的 PostgreSQL 容器健康、连接和持久化验证全部通过；
- 任务 08 不阻塞当前版本上线，依赖员工导入和查询 API 的稳定性。

## Future：扩容与托管迁移（不属于 v1）

| 任务 | 触发条件 | 内容 |
|---|---|---|
| F-1 | 单机 CPU、内存或磁盘成为瓶颈 | 将 PostgreSQL 迁移到腾讯云数据库，必要时拆分前端静态资源与应用服务，API 保持不变 |
| F-2 | 导入任务需要异步队列或更长执行时间 | 增加任务队列、对象存储和异步任务状态 |
| F-3 | 需要多机高可用 | 拆分 API、数据库和备份服务，增加负载均衡 |
| F-4 | 服务器维护成本超过预算 | 评估腾讯云托管 PostgreSQL 或其他托管 PostgreSQL |

### v1 迁移验收约束

- 页面组件只依赖前端 services，不依赖 PostgreSQL 驱动；
- Node.js API 通过稳定业务接口隔离数据库实现；
- `employee_work_batches`、`employee_work_items`、`pricing_batches`、`pricing_items` 和 `app_users` 的业务字段保持稳定；
- `created_by` 始终由服务端从已验证登录身份产生；
- 至少保留一份可恢复的 PostgreSQL 备份；
- 服务器故障时可在新服务器重新部署 Compose 栈并恢复数据库，再切换域名；
- v1 不使用 Kubernetes、负载均衡和多机集群，只有达到扩容触发条件后再引入。
