# 任务拆分与排期（v2.2）

> 单人开发，核心 v1 预计 10~13 个工作日。主架构为同一台腾讯云轻量应用服务器上的 Nginx + React/Vite + Hono.js/Node.js API + Drizzle ORM + PostgreSQL，使用 Docker Compose 管理服务。任务按纵向切片拆分，每个任务完成后都具备可演示或可验证的端到端行为。

## 范围与顺序

| 编号 | 任务 | 版本 | 阻塞关系 | 估时 |
|---|---|---|---|---|
| 01 | Hono.js/Node.js 后端与数据库基础 | v1 | 无 | 2~3 天 |
| 02 | 认证、权限与 Hono API | v1 | 01 | 2~3 天 |
| 03 | Excel 导入与失败恢复 | v1 | 01、02 | 2~3 天 |
| 04 | 商品列表与上传人筛选 | v1 | 01、02 | 1~2 天 |
| 05 | 内部备注编辑 | v1 | 01、02、04 | 1 天 |
| 06 | 腾讯云轻量服务器部署与上线验收 | v1 | 01、02、03、04、05 | 2~3 天 |
| 07 | v1.1 扩展功能 | v1.1 | 03、04、05 | 3~5 天 |

v1 的核心路径为：登录 → 导入 Excel → 查看/筛选商品 → 编辑内部备注。v1 不做操作审计、修改历史和删除记录。

## 01：Hono.js/Node.js 后端与数据库基础

**优先级**：P0

**交付**：初始化 Hono.js + Node.js + TypeScript 后端项目，配置 PostgreSQL 连接和 Drizzle ORM；完成 `drizzle-orm`、`drizzle-kit` 的 schema 与迁移流程，建立 `app_users`、`products`、`import_batches` 数据结构、索引和约束。服务器和公网部署在任务 06 完成。

**验收标准**：

- Hono.js 后端可以在 Node.js 上启动，TypeScript 编译和依赖 lockfile 检查通过；
- PostgreSQL 连接配置通过环境变量提供，使用连接池和参数化查询，数据库连接失败时应用给出明确错误；
- `drizzle-orm` schema 与 PostgreSQL 表结构一致，`drizzle-kit` 可以生成并执行版本化迁移；
- 完成三张业务表、外键、检查约束、列表筛选索引和迁移脚本；
- `created_by`、`created_at`、`updated_at`、`batch_id` 等系统字段由 API 和数据库约束保护；
- 数据库密码、JWT 密钥和备份凭据通过环境变量或受限文件提供，不进入仓库和前端构建产物；
- 完成数据库连接、迁移和基础 schema 的自动化测试；
- v1 不开放商品删除、商品字段编辑和批次回滚能力，相关能力留到任务 07。

## 02：认证、权限与 Hono API

**优先级**：P0

**阻塞于**：任务 01

**交付**：使用 Hono.js 在 Node.js 上提供健康检查、认证、权限和业务 API；完成邮箱密码登录、JWT 登录态、团队成员准入、角色权限中间件、统一错误处理和环境变量校验。前端通过 API 访问业务数据，不直接连接数据库。

**验收标准**：

- API 提供健康检查、登录、当前用户和退出接口，已开通成员可以登录并获得有效登录令牌；
- 密码使用安全哈希保存，接口不返回密码哈希，登录失败不泄露账号是否存在；
- 只有 `app_users.is_active = true` 的成员可以访问业务 API，未开通账号得到明确的无权限响应；
- API 从 JWT 确定当前用户，客户端伪造 `created_by`、角色或用户 ID 不会改变服务端身份；
- `owner` 和 `selector` 可以调用导入相关接口，`operator` 只能查看商品和编辑内部备注；
- API 与数据库访问通过 service/repository 层和 Drizzle ORM 封装，前端页面不直接调用数据库驱动；
- 请求参数和响应结构使用 Zod 或等效 schema 校验，统一返回错误码、错误消息和 HTTP 状态码；
- 缺少或错误的环境变量、无效令牌、权限不足和数据库异常都有明确且不泄露敏感信息的错误响应；
- 后端测试覆盖登录、令牌失效、成员准入、角色权限和伪造身份字段；
- 本地开发环境可以重复验证登录、令牌失效和路由保护。

## 03：Excel 导入与失败恢复

**优先级**：P0

**阻塞于**：任务 01、任务 02

**交付**：选品员通过 Hono.js API 上传固定模板 Excel，可以看到解析、写入和结果进度；服务端自动绑定当前成员、创建时间和批次；导入失败可以定位并重试，重试不会重复写入已成功的数据。

**验收标准**：

- 支持 `.xlsx` 和 `.xls`，并对表头、空文件、商品名称、价格格式和 5 万行上限进行校验；
- Excel 文件上传到 Hono.js API 后由 Node.js 服务端解析和分块处理，浏览器不直接向数据库批量写入；
- 导入页面展示待处理行数、成功写入数、总行数和当前状态；
- 每次导入生成批次记录，包含文件名、上传人、时间、状态、总数、成功数、失败数和错误范围；
- 每行数据自动关联当前登录成员、创建时间和批次 ID，客户端不能覆盖系统字段；
- 部分失败时保留失败范围和错误原因，支持从失败位置重试且不会产生重复数据；
- 真实腾讯云服务器环境下 5 万行导入在 2 分钟内完成，页面结果与批次结果一致；
- 导入接口测试覆盖文件类型、行数上限、权限不足、部分失败和重复重试场景。

## 04：商品列表与上传人筛选

**优先级**：P0

**阻塞于**：任务 01、任务 02

**交付**：登录成员可以分页浏览团队商品，并按上传人筛选；列表展示商品核心字段和导入追溯信息，适用于几十万行数据规模。

**验收标准**：

- 商品列表使用 API 服务端分页，每页 100 条，翻页不重复、不遗漏；
- 可以按已开通成员筛选上传人，结果与商品归属一致；
- 列表展示货号、商品名称、平台、价格、规格、链接、上传人、上传时间和内部备注；
- 50 万行数据下分页和上传人筛选使用索引，真实服务器环境 p95 响应时间小于 1 秒；
- 未登录或未开通账号不能通过 API 读取业务数据；
- 链接字段按普通文本展示，外部跳转行为不阻塞 v1 核心验收。

## 05：内部备注编辑

**优先级**：P0

**阻塞于**：任务 01、任务 02、任务 04

**交付**：任意已登录团队成员可以在线编辑商品内部备注并保存；多人同时编辑同一条备注时采用最后写入覆盖，且编辑备注不会改变其他商品字段。

**验收标准**：

- 列表中的内部备注支持编辑、保存和失败提示，保存后刷新内容仍然存在；
- 任意已登录团队成员都可以编辑内部备注，不受商品上传人限制；
- API 更新请求只允许修改内部备注和系统更新时间，不能修改商品归属、批次或原始导入字段；
- 两个成员先后保存同一条备注时，最终内容以最后一次成功写入为准；
- 网络或权限错误时显示保存失败，并以服务端数据恢复展示；
- v1 不记录备注修改人、修改历史、旧值和新值。

## 06：腾讯云轻量服务器部署与上线验收

**优先级**：P0

**阻塞于**：任务 01、任务 02、任务 03、任务 04、任务 05

**交付**：将 React/Vite 构建产物、Hono.js/Node.js API 和 PostgreSQL 部署到同一台腾讯云轻量应用服务器，使用 Docker Compose 管理服务，Nginx 提供前端静态文件、反向代理和 HTTPS，完成日志、备份、恢复演练和团队并发验收。

**验收标准**：

- 腾讯云轻量服务器完成 Ubuntu、Docker、Docker Compose 和域名配置，Nginx、Hono.js/Node.js API、PostgreSQL 由 Compose 管理并可开机自启和异常重启；
- React/Vite 构建产物由服务器上的 Nginx 提供，通过正式 HTTPS 域名访问；Nginx 将 `/api` 请求转发到 Compose 内部的 Hono.js API；
- Nginx 配置 HTTPS 证书、自动续期和到期检查，前端与 API 的访问链路可验证；
- Hono.js API 和 PostgreSQL 只加入 Compose 内部网络，防火墙只开放 80、443 和受限制的 SSH 端口，数据库端口不对公网开放；
- 生产环境通过环境变量注入数据库连接、JWT 密钥、Cookie 签名密钥和第三方凭据，不暴露敏感管理密钥；
- Nginx 访问日志、错误日志、Hono.js 应用日志和 PostgreSQL 日志按天切分并保留，健康检查可以发现 API 或数据库异常；
- 每日执行 `pg_dump` 并上传到服务器外部存储，至少保留 7~14 天，完成一次新服务器恢复演练；
- 记录 CPU、内存、磁盘和 5 万行导入期间的资源峰值，确认资源限制不会导致服务异常；
- 3 名团队成员同时完成登录、筛选和备注编辑，无明显卡顿或数据串写；
- 核心路径“登录 → 导入 → 筛选 → 改备注”完整跑通，5 万行导入达到任务 03 的标准。

## 07：v1.1 扩展功能

**优先级**：P1

**阻塞于**：任务 03、任务 04、任务 05

**交付**：在 v1 稳定运行后，增加管理员和成员管理、商品查找、授权数据维护及批次回滚能力，同时保持 v1 的导入追溯和备注编辑行为不变。

**验收标准**：

- 管理员可以管理团队成员和角色，非管理员不能执行成员管理操作；
- 支持按平台筛选，以及按货号或商品名称模糊搜索；
- 上传人可以删除自己导入的商品，管理员可以按授权规则删除任意商品；
- 授权用户可以编辑货号、价格等商品字段，但系统字段仍受保护；
- 批次管理页可以查看导入历史，并执行可确认、可恢复的整批回滚；
- v1.1 不包含操作审计、修改历史和删除日志。

## 依赖关系

- 任务 01 是 Drizzle schema、数据库、认证、API、导入、列表和备注编辑的共同基础；
- 任务 02 必须在任务 01 完成数据库和服务器基线后开始；
- 任务 03 依赖任务 01 的 Drizzle schema/迁移，以及任务 02 的登录态和权限中间件；
- 任务 04 可以与任务 03 并行开发，但必须依赖任务 01 的索引和任务 02 的受保护 API；
- 任务 05 依赖任务 04 的列表交互，并复用任务 02 的字段级更新权限和任务 01 的 Drizzle 更新模型；
- 任务 06 必须等待 v1 核心链路完成；
- 任务 07 不阻塞 v1 上线，依赖导入、列表和备注编辑的稳定 API。

## 工作量汇总

| 范围 | 估时 |
|---|---|
| v1（任务 01~06） | 10~13 个工作日 |

> 以上为单人开发预估。任务 01~02 的耗时受 Hono.js API、Drizzle 迁移、认证和错误处理影响；任务 03 的耗时受大文件导入和服务器内存表现影响；任务 06 的耗时受域名、Nginx、证书、日志和备份配置影响，应以真实数据验证结果为准。

## Future：扩容与托管迁移（不属于 v1）

| 任务 | 触发条件 | 内容 |
|---|---|---|
| F-1 | 单机 CPU、内存或磁盘成为瓶颈 | 将 PostgreSQL 迁移到腾讯云数据库，必要时拆分前端静态资源与应用服务，API 保持不变 |
| F-2 | 导入任务需要异步队列或更长执行时间 | 增加任务队列、对象存储和异步任务状态 |
| F-3 | 需要多机高可用 | 拆分 API、数据库和备份服务，增加负载均衡 |
| F-4 | 服务器维护成本超过预算 | 评估腾讯云托管 PostgreSQL 或其他托管 PostgreSQL |

### v1 迁移验收约束

- 页面组件只依赖前端 services，不依赖 PostgreSQL 驱动；
- Node.js API 通过稳定业务接口隔离数据库实现；
- `products`、`app_users`、`import_batches` 的业务字段保持稳定；
- `created_by` 始终由服务端从已验证登录身份产生；
- 至少保留一份可恢复的 PostgreSQL 备份；
- 服务器故障时可在新服务器重新部署 Compose 栈并恢复数据库，再切换域名；
- v1 不使用 Kubernetes、负载均衡和多机集群，只有达到扩容触发条件后再引入。
