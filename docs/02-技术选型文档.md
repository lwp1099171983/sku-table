# 技术选型文档（v2.3）

## 1. 决策目标与约束

- 目标：国内稳定、成本可控、由自动化脚本和 AI 辅助维护的内部工具。
- 约束：
  - 前端：React / Vite / TypeScript；
  - 数据：≤ 50 万行、单条约 500 字节、3~5 人并发；
  - 成本：腾讯云轻量应用服务器约 20~50 元/月，以实际套餐为准；
  - 核心需求：上传人防伪造、内部备注在线编辑、5 万行批量导入；
  - 部署：不使用 Kubernetes，不提前拆分多台服务器。

项目代码采用 npm workspaces 管理，前端位于 `apps/web`，Hono.js API 位于 `apps/api`，共享 DTO 和领域类型位于 `packages/shared`，Docker/Nginx/运维配置位于 `infra`。历史 Supabase 迁移材料仅保留在 `infra/legacy/supabase`，不参与 v1 主流程。

## 2. 方案对比

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 纯前端 + localStorage | 零成本、零部署 | 无法多用户、数据存本地 | ❌ 排除 |
| Vercel + Supabase | 生态成熟、托管数据库 | 国内访问和网络稳定性不符合要求 | ❌ 排除 |
| 腾讯云开发 CloudBase | 国内访问、免服务器 | 文档型数据和资源点模型不适合大批量导入 | ⚠️ 备用 |
| **腾讯云轻量应用服务器 + Hono.js + Node.js + Drizzle ORM + PostgreSQL** | 成本可控、数据库和 API 完全可控、适合批量导入 | 需要配置安全、备份和升级 | ✅ **主方案** |
| 云数据库 + 云托管 API | 托管程度高、稳定性好 | 成本可能超过当前预算，架构复杂度更高 | 🔧 后续升级 |

## 3. 选型结论

### 3.1 服务器：腾讯云轻量应用服务器

采用一台国内节点的腾讯云轻量应用服务器作为 v1 起步生产环境：

- 系统：Ubuntu 24.04 LTS；
- 起步配置：2 核 CPU、4 GB 内存、80 GB SSD、3~5 Mbps 公网带宽；
- 必须有公网 IPv4，地域选择靠近团队用户的大陆节点；
- PostgreSQL 和 Node.js API 先部署在同一台服务器，降低成本和运维复杂度；
- React/Vite 构建产物由同一台服务器上的 Nginx 提供静态访问，前端、API 和数据库共用服务器资源；
- 后续数据量或负载增长，再把 PostgreSQL 迁移到云数据库，不改变业务 API 接口。

### 3.2 后端：Hono.js + Node.js + TypeScript

Hono.js API 运行在 Node.js 上，负责认证、业务权限、Excel 导入、批次处理、列表查询和备注更新，不让浏览器直接连接数据库。

- Hono.js：路由和中间件简洁，适合构建轻量 TypeScript API；
- `@hono/node-server`：提供 Node.js 运行时适配；
- TypeScript：约束 API 输入输出和数据库模型；
- `drizzle-orm`：提供类型安全的 PostgreSQL 查询和 schema 定义；
- `drizzle-kit`：管理 schema 推送、迁移生成和迁移执行；
- `pg`：提供 PostgreSQL 连接池；
- Hono JWT 中间件或 `jose`：验证登录令牌；
- `zod`：校验请求参数和导入数据；
- `xlsx`：服务端解析 Excel，避免浏览器内存和网络分批写入的不稳定；
- API 从服务端认证身份生成 `created_by`，不信任客户端传入的用户 ID。

### 3.3 认证与权限

v1 采用邮箱+密码登录，账号由负责人预先创建或通过受控管理脚本开通，不开放公开注册。Hono.js 通过认证中间件验证 JWT，并在服务端执行以下规则：

- 只有 `app_users.is_active = true` 的团队成员可以访问业务 API；
- `owner` 和 `selector` 可以导入 Excel；
- 所有团队成员可以查看商品和编辑 `internal_note`；
- v1 不提供删除、商品字段编辑和批次回滚；
- 系统字段 `created_by`、`created_at`、`updated_at`、`batch_id` 由服务端和 PostgreSQL 约束保护；
- API 不接受客户端传入的身份、角色和创建人字段，所有写入身份从已验证令牌中获取；
- 商品更新接口只允许修改 `internal_note`，避免普通成员修改原始导入字段。

### 3.4 数据库：PostgreSQL

使用标准 PostgreSQL 保存 `app_users`、`products`、`import_batches` 三张业务表，并由 Drizzle ORM 管理 schema、类型和迁移。保留索引、外键、检查约束和事务边界。

- `drizzle-orm` 使用 PostgreSQL 方言和参数化查询，后端服务通过连接池访问数据库；
- `drizzle-kit` 配置 schema 入口、迁移目录和数据库连接，用于生成和执行版本化迁移；
- 商品列表按 `created_by`、`batch_id` 和主键建立索引；
- 导入批次记录状态、总行数、成功行数、失败行数和错误信息；
- 导入批次采用事务和幂等键，失败后可从失败位置重试，不重复写入成功数据；
- 备注更新使用最后写入覆盖，v1 不记录修改历史；
- PostgreSQL 只监听本机或私有网络，不开放公网数据库端口；
- 数据库账号采用最小权限，生产 API 不使用超级用户连接。

### 3.5 前端：React + Vite + Ant Design

- React + Vite + TypeScript；
- Ant Design 5 覆盖表格、筛选、表单、上传、进度和分页；
- 前端只调用 Hono.js API，通过 `src/services/` 封装认证、商品和导入服务；
- 商品列表使用服务端分页，每页 100 条，不把几十万行加载到浏览器；
- 不同时引入第二套 UI 组件库。

## 4. 部署架构

```text
用户浏览器
    ↓ HTTPS
腾讯云轻量应用服务器
    └─ Docker Compose
        ├─ Nginx（React/Vite 静态文件、HTTPS、反向代理）
        │       ↓ Docker 内部网络
        ├─ Hono.js + Node.js API
        │       ↓ Docker 内部网络
        └─ PostgreSQL（持久化数据卷）
```

腾讯云轻量应用服务器承载前端、Hono.js/Node.js API 和 PostgreSQL。Docker Compose 管理服务编排、启动顺序和异常重启，Nginx 负责唯一公网入口，备份脚本负责数据库保护。生产接入分两个严格顺序的阶段：先部署 Compose 栈并验证 PostgreSQL，再启用 COS 自动备份。

- Nginx 只暴露 80/443，提供 React/Vite 构建产物，并将 `/api` HTTPS 请求转发到 Docker 内部的 Hono.js API；
- 使用 Let's Encrypt 或腾讯云证书配置 HTTPS，并设置自动续期和到期检查；
- Docker Compose 为 Nginx、API 和 PostgreSQL 设置健康检查及异常重启，服务器通过 systemd 配置 Compose 栈开机启动；
- Hono.js API 只加入 Docker 内部网络，不直接暴露宿主机端口；
- PostgreSQL 只加入数据库内部网络并使用持久化数据卷，不绑定公网地址；
- 数据库密码、JWT 密钥、Cookie 签名密钥和备份凭据只存服务器环境变量或受限密钥文件；
- 防火墙只开放 80、443，以及限制来源后的 SSH 端口；
- 前端与 API 使用同一 HTTPS 域名时优先采用同源请求；如存在跨域访问，API 仅配置明确的 HTTPS 来源白名单；
- Nginx、Hono.js 和 PostgreSQL 日志按天切分并保留，避免日志占满服务器磁盘；
- 前端构建产物不包含数据库连接串、JWT 密钥、Cookie 签名密钥或备份凭据。

## 5. 备份与运维

### 5.1 Docker Compose 与 PostgreSQL 基线验证

- 腾讯云服务器已完成 COS 基础配置，但不在数据库尚未验证时启用定时备份；
- 先部署 Docker Compose，确认 PostgreSQL 容器为 `healthy`、持久化数据卷已挂载、数据库可连接；
- 执行迁移和最小读写检查，重启 PostgreSQL 容器后再次验证数据仍在，确认持久化配置有效；
- 只有上述验收全部通过，才进入 COS 自动备份接入阶段。

### 5.2 每日 `pg_dump` → COS

- 定时任务每日对 PostgreSQL 执行 `pg_dump`，将带时间戳的备份文件上传到已配置的腾讯云 COS，本地临时文件在上传成功后清理；
- COS 密钥、Bucket、Region 和路径前缀仅通过服务器环境变量或受限配置文件提供，不进入仓库和容器镜像；
- 备份脚本必须在 `pg_dump` 失败、COS 上传失败或上传后对象校验失败时返回非零状态，不得将未上传成功记录为成功；
- 至少保留最近 7~14 天备份，并定期清理过期备份；
- 每月至少做一次恢复演练，验证可在新服务器或隔离恢复环境中恢复数据库并启动 API；
- 备份脚本记录开始时间、结束时间、文件大小、COS 对象路径和成功/失败状态，失败时通过日志或告警暴露；

### 5.3 其他运维要求

- API 提供健康检查接口，部署脚本执行容器状态、数据库连接和迁移检查；
- 使用 lockfile 固定 Node.js 依赖版本，生产部署前执行 `drizzle-kit` 迁移；
- Docker Compose、systemd、Nginx 和 PostgreSQL 的日志纳入统一检查范围；
- 记录服务器规格、磁盘使用率、内存使用率和导入期间资源峰值；达到资源阈值时暂停大批量导入并评估扩容；
- AI 用于生成部署脚本、分析日志和辅助升级，但生产变更仍需人工确认。

## 6. 迁移与回退

代码和数据按“服务层隔离、数据库标准化”设计：

```text
当前：浏览器 → Nginx（React/Vite + HTTPS）→ Hono.js/Node.js API → Drizzle ORM → PostgreSQL
扩容：浏览器 → Nginx 或静态托管 → Hono.js/Node.js API → Drizzle ORM → 托管 PostgreSQL
```

- API 层隔离数据库实现，前端不依赖数据库驱动或 ORM；
- 使用标准 PostgreSQL 类型、标准 SQL、UUID 和时间戳；
- 保留 `products`、`app_users`、`import_batches` 的稳定业务字段；
- 如果服务器故障，先创建同规格或更高规格的新服务器，重新部署 Docker Compose，再从服务器外部备份恢复 PostgreSQL，最后切换 API 域名；
- v1 以每日备份为恢复边界，目标 RPO 不超过 24 小时；恢复时间通过新服务器恢复演练验证，不承诺单机故障期间持续可用；
- 如果数据规模增长，再将 PostgreSQL 迁移到腾讯云数据库，API 和前端接口保持稳定。

## 7. 风险与应对

| 风险 | 应对 |
|---|---|
| 单机故障 | PostgreSQL 验收后再启用每日 `pg_dump` → COS，准备新服务器恢复流程 |
| COS 上传或凭据异常 | 使用最小权限凭据，上传后校验对象，定时任务失败时保留日志并告警 |
| 磁盘或内存不足 | 限制单批 5 万行，监控磁盘和内存，清理日志并按需升级服务器配置 |
| 服务器入侵或密钥泄露 | 仅开放必要端口，SSH 使用密钥，密钥不进仓库，定期升级镜像 |
| 批量导入占满内存 | 服务端流式或分块处理，限制单批 5 万行，导入期间监控内存 |
| HTTPS 或域名配置失败 | 先用服务器 IP 做 API 健康检查，再绑定正式域名和证书 |
| 预算超出 | 先保持单机部署，不购买云数据库、负载均衡和 Kubernetes |
| 服务器维护复杂 | 使用 Docker Compose、systemd、自动备份、健康检查和 AI 辅助排障 |
| 需要更复杂权限或异步任务 | 增加队列或拆分 API 服务，不改变前端业务接口 |

## 8. v1 不做的技术投入

- 不使用 Kubernetes、服务网格和多机集群；
- 不提前购买云数据库、负载均衡和消息队列；
- 不让浏览器直接访问 PostgreSQL；
- 不让前端直接使用 Drizzle ORM 或数据库连接字符串；
- 不把数据库密码、JWT 密钥或备份凭据放入前端；
- 不在 v1 引入操作审计、修改历史和删除日志；
- 只保留清晰的前端 services、Hono.js API 接口、Drizzle schema/迁移、标准 SQL 和备份流程。
