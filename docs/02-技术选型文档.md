# 技术选型文档（v2.4）

## 1. 决策目标与约束

- 目标：国内稳定、成本可控、由自动化脚本和 AI 辅助维护的内部工具。
- 约束：
  - 前端：React / Vite / TypeScript；
  - 数据：≤ 50 万行、单条约 500 字节、3~5 人并发；
  - 成本：腾讯云轻量应用服务器约 20~50 元/月，以实际套餐为准；
  - 核心需求：按店铺隔离、Excel 批量导入、台账统计汇总、删除权限可配置；
  - 部署：不使用 Kubernetes，不提前拆分多台服务器。

项目代码采用 pnpm workspaces 管理，前端位于 `apps/web`，Hono.js API 位于 `apps/api`，共享 DTO 和领域类型位于 `packages/shared`，Docker/Nginx/运维配置位于 `infra`。历史 Supabase 迁移材料仅保留在 `infra/legacy/supabase`，不参与 v1 主流程。

## 2. 方案对比

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 纯前端 + localStorage | 零成本、零部署 | 无法多用户、数据存本地 | ❌ 排除 |
| Vercel + Supabase | 生态成熟、托管数据库 | 国内访问和网络稳定性不符合要求 | ❌ 排除 |
| 腾讯云开发 CloudBase | 国内访问、免服务器 | 文档型数据和资源点模型不适合大批量导入 | ⚠️ 备用 |
| **腾讯云轻量应用服务器 + Hono.js + Node.js + Drizzle ORM + PostgreSQL** | 成本可控、数据库和 API 完全可控、适合批量导入 | 需要配置安全、备份和升级 | ✅ **主方案** |
| 云数据库 + 云托管 API | 托管程度高、稳定性好 | 成本可能超过当前预算，架构复杂度更高 | 🔧 后续升级 |

## 3. 选型结论

### 3.1 服务器：腾讯云轻量应用服务器

采用一台国内节点的腾讯云轻量应用服务器作为 v1 起步生产环境：

- 系统：Ubuntu 24.04 LTS；
- 起步配置：2 核 CPU、4 GB 内存、80 GB SSD、3~5 Mbps 公网带宽；
- 必须有公网 IPv4，地域选择靠近团队用户的大陆节点；
- PostgreSQL 和 Node.js API 先部署在同一台服务器，降低成本和运维复杂度；
- React/Vite 构建产物由同一台服务器上的 Nginx 提供静态访问，前端、API 和数据库共用服务器资源；
- 后续数据量或负载增长，再把 PostgreSQL 迁移到云数据库，不改变业务 API 接口。

### 3.2 后端：Hono.js + Node.js + TypeScript

Hono.js API 运行在 Node.js 上，负责认证、业务权限、Excel 导入、批次处理和列表查询，不让浏览器直接连接数据库。

- Hono.js：路由和中间件简洁，适合构建轻量 TypeScript API；
- `@hono/node-server`：提供 Node.js 运行时适配；
- TypeScript：约束 API 输入输出和数据库模型；
- `drizzle-orm`：提供类型安全的 PostgreSQL 查询和 schema 定义；
- `drizzle-kit`：管理 schema 推送、迁移生成和迁移执行；
- `pg`：提供 PostgreSQL 连接池；
- Hono JWT 中间件或 `jose`：验证登录令牌；
- `zod`：校验请求参数和导入数据；
- `xlsx`：服务端解析 Excel，避免浏览器内存和网络分批写入的不稳定；
- API 使用 JSON 结构化运行日志：全局记录请求方法、路径、状态码和耗时，台账导入记录文件元信息、解析统计、入库结果和错误摘要；不记录业务明细、JWT 或密码；
- API 从服务端认证身份生成 `created_by`，不信任客户端传入的用户 ID。

### 3.3 认证与权限

采用邮箱+密码登录，管理员账号全局（`is_admin = true`），组长/客服账号由管理员创建并分配到店铺。JWT 只保存用户 ID，不保存角色和权限；权限按"当前店铺"由服务端实时计算，客户端无法通过伪造令牌字段提权。

- `app_users` 保存身份、启用状态和全局管理员标记（`is_admin`），角色改由 RBAC 表管理；
- 账号通过 `shop_members` 加入店铺，成员关系与权限按店铺生效；
- 权限采用默认拒绝模型：有效权限 = 角色 allow + 用户级 allow − 用户级 deny（deny 优先）；
- 预置角色：`admin`（全局、全部权限）、`leader`（查看/导入员工工作与台账明细，不含台账统计）、`customer`（查看/导入员工工作）；
- 13 个权限码按业务域分组（shop、member、employee_work、ledger），`ledger.stats.read` 仅预置给管理员；台账编辑和删除类权限（`ledger.edit` / `employee_work.delete` / `ledger.delete`）由管理员按用户、按店铺开通 allow/deny；
- API 写操作继续通过 `requirePermission(权限码)` 校验当前店铺权限；只读列表由店铺范围解析器逐店铺校验查看权限并过滤实际数据范围；`requireShopPermission` 针对路径参数 `:shopId` 校验成员关系与目标店铺权限；删除接口按请求携带的 `shopId` 逐店铺校验权限；
- "全部店铺"视图：`currentShop` 为 null；管理员返回系统全部店铺，多店铺组长/客服登录后由前端自动切换到该视图，并仅返回本人被分配且具备对应查看权限的店铺，列表显示店铺列；
- 系统字段 `uploaded_by`、`created_at`、`batch_id`、`shop_id` 由服务端和 PostgreSQL 约束保护；
- API 不接受客户端传入的身份、角色、权限和创建人字段，所有写入身份从已验证令牌中获取；
- 台账导入保留来源字段；尾程为空时默认 `2%`，并用固定汇率重算毛利、净利及广告净利；仅 `ledger.edit` 权限允许通过重量编辑接口重算运费、抽点等相关公式列。物流资费仅管理员可通过 `/admin/shipping-rates` 导入、查看和启用，沿用只授予管理员的 `user.manage` 权限。

### 3.4 数据库：PostgreSQL

使用标准 PostgreSQL 保存业务与 RBAC 表：`app_users`、`shops`、`shop_members`、`roles`、`permissions`、`role_permissions`、`shop_member_roles`、`shop_member_permissions`、`employees`、`employee_work_batches`、`employee_work_items`、`ledger_batches`、`ledger_items`、`shipping_rate_versions`、`shipping_rates`，并由 Drizzle ORM 管理 schema、类型和迁移。保留索引、外键、检查约束和事务边界。

- 所有业务根表带 `shop_id NOT NULL`，子表使用 `(batch_id, shop_id)` 组合外键引用批次，防止跨店铺关联；
- `employee_work_batches.employee_id` 引用 `employees.id`（组合外键），`employee_name` 保留导入快照；
- 检查约束：批次行数 0~50000，文件名/员工名/店铺名非空且限长，员工工作金额非负；统一 `updated_at` 触发器；批次表预留 `archived_at` / `archived_by`，默认查询排除归档；
- 员工工作索引：`(shop_id, employee_name, work_date desc, id desc)`、`(shop_id, work_date desc, id desc)`、`(shop_id, batch_id, id desc)`、`(shop_id, created_at desc)`，服务端按页查询；
- 台账明细 25 个业务字段全部 `text` 保存原始值，`tracking_no` 已迁移为 `sku`、`compensation` 已迁移为 `tail_fee`；尾程比例按 `apps/api/src/config/exchangeRate.ts` 的固定汇率换算为人民币后参与利润计算；统计在应用层对数字求和、非数字文本按 0 处理；
- 台账索引：`(shop_id, batch_id, id desc)`、`(shop_id, month)`、`(order_month)`，订单号使用全系统非空唯一索引；SKU 不做唯一约束；
- 物流资费：`shipping_rate_versions` 保存版本来源、启用状态和操作时间，部分唯一索引保证同时只有一个启用版本；`shipping_rates` 以版本、渠道、基础价格、每克价格、最小/最大计费重量保存规则。重量重算在同一事务读取启用规则并写入 `ledger_items.shipping_rate_version_id`，源 Excel 原始导入行保持空版本；
- 模糊搜索：`pg_trgm` GIN 索引覆盖员工工作 SKU/名称；普通 B-tree SKU 索引只用于精确匹配；
- 迁移执行器使用固定 key 的 PostgreSQL advisory lock，避免多个 API 实例并发执行迁移，迁移在事务中执行、失败整体回滚；
- 迁移策略：基线迁移 `0001_initial_baseline.sql` 面向空库执行（店铺体系 + 员工工作 + 台账）；`0002`~`0007` 依次完成定价下线、店铺重构、台账 text 化、导入幂等、RBAC 目录和统计权限；`0008` 迁移 SKU、订单唯一与台账编辑权限；`0009_customer_employee_work_import.sql` 为客服角色补充员工工作导入权限；`0010_ledger_order_month_range.sql` 增加并回填可索引的订单年月；`0011_ledger_tail_fee.sql` 迁移尾程字段并回算历史利润；`0012_shipping_rate_versions.sql` 新增资费版本与规则表并迁入 89 条初始规则；`0013_ledger_soft_delete.sql` 增加台账软删除字段，并将订单号唯一约束限定为当前台账；旧库与空库均按迁移序列执行；生产执行前必须 `pg_dump`；
- seed 幂等：角色/权限目录 upsert、管理员账号（`is_admin = true`）、默认店铺（`SEED_SHOP_NAME` 或"默认店铺"），可重复执行；
- 员工工作批次和明细使用事务写入，失败时整体回滚，不留下孤立明细；
- 导入幂等：批次表记录"解析后业务数据的规范化 SHA-256"（排除自动序号；员工工作含店铺/员工/日期维度），`(shop_id, 指纹)` 唯一索引 + `onConflictDoNothing`，同一份数据重复导入直接复用已有批次，避免超时重试或重复上传造成重复入库；指纹基于数据行而非文件字节，不受 Excel 保存产生的元数据变化影响；
- 员工工作货号去重：货号解析后去除首尾空白，同一店铺内按小写货号比较；先在文件内保留第一条，再在持有店铺行锁的事务中查询已有货号并过滤，确保同店铺并发导入不会写入重复货号；接口返回实际新增行数与跳过行数，批次 `total_rows` 仅记录实际入库行数；
- 台账订单号去重：非空订单号去除首尾空格后按全系统、区分大小写唯一；文件内跨店铺保留第一条，历史与并发冲突依靠 PostgreSQL 部分唯一索引跳过；空订单号和重复 SKU 均允许写入；
- 重量计算：物流资费以 `shipping_rate_versions` + `shipping_rates` 保存，初始版本迁入源 Excel 的 89 条规则；管理员通过 API 和页面导入新版 Excel，规则解析后默认未启用，事务内切换为唯一启用版本。重量编辑在同一事务内读取启用规则，以 `decimal.js` 十进制计算运费、尾程、毛利、抽点、净利与广告利润，并把 `shipping_rate_version_id` 写入台账；固定卢布兑人民币汇率配置在 `config/exchangeRate.ts`，尾程按比例计算、限制 `15~200 RUB` 后换算人民币；金额结果按 `ROUND_HALF_UP` 固定为两位，统计使用十进制累加后保留两位；非法数字、未知渠道和超重返回 422 且不写入；
- `drizzle-orm` 使用 PostgreSQL 方言和参数化查询，后端服务通过连接池访问数据库；
- PostgreSQL 只监听本机或私有网络，不开放公网数据库端口；
- 数据库账号采用最小权限，生产 API 不使用超级用户连接。

### 3.5 前端：React + Vite + Ant Design

- React + Vite + TypeScript；
- Ant Design 5 覆盖表格、筛选、表单、上传、进度和分页；
- 前端只调用 Hono.js API，通过 `src/services/` 封装认证、员工工作记录、台账、店铺与成员、物流资费服务；
- 台账重量使用 `InputNumber` 行内编辑，前后端双重校验为非负有限数字，保存后刷新明细和顶部统计；
- 员工工作明细使用服务端分页，每页 100 条，不把几十万行加载到浏览器；多文件导入由前端按文件顺序逐个调用单文件导入接口，每个文件保持独立事务、幂等指纹和批次追溯，单个文件失败不影响其他文件；纯客服导入的员工姓名由服务端从认证账号生成，不信任客户端字段；
- 不同时引入第二套 UI 组件库。

## 4. 部署架构

```text
用户浏览器
    ↓ HTTPS
腾讯云轻量应用服务器
    └─ Docker Compose
        ├─ Nginx（React/Vite 静态文件、HTTPS、反向代理）
        │       ↓ Docker 内部网络
        ├─ Hono.js + Node.js API
        │       ↓ Docker 内部网络
        └─ PostgreSQL（持久化数据卷）
```

腾讯云轻量应用服务器承载前端、Hono.js/Node.js API 和 PostgreSQL。Docker Compose 管理服务编排、启动顺序和异常重启，Nginx 负责唯一公网入口，备份脚本负责数据库保护。生产接入分两个严格顺序的阶段：先部署 Compose 栈并验证 PostgreSQL，再启用 COS 自动备份。

- Nginx 只暴露 80/443，提供 React/Vite 构建产物，并将 `/api` HTTPS 请求转发到 Docker 内部的 Hono.js API；
- 使用 Let's Encrypt 或腾讯云证书配置 HTTPS，并设置自动续期和到期检查；
- Docker Compose 为 Nginx、API 和 PostgreSQL 设置健康检查及异常重启，服务器通过 systemd 配置 Compose 栈开机启动；
- Hono.js API 只加入 Docker 内部网络，不直接暴露宿主机端口；
- PostgreSQL 只加入数据库内部网络并使用持久化数据卷，不绑定公网地址；
- 数据库密码、JWT 密钥、Cookie 签名密钥和备份凭据只存服务器环境变量或受限密钥文件；
- 防火墙只开放 80、443，以及限制来源后的 SSH 端口；
- 前端与 API 使用同一 HTTPS 域名时优先采用同源请求；如存在跨域访问，API 仅配置明确的 HTTPS 来源白名单；
- Nginx、Hono.js 和 PostgreSQL 日志通过容器日志轮转限制大小并保留；Hono.js 正常健康检查不写访问日志，避免高频噪声占用磁盘；
- 前端构建产物不包含数据库连接串、JWT 密钥、Cookie 签名密钥或备份凭据。

## 5. 备份与运维

### 5.1 Docker Compose 与 PostgreSQL 基线验证

- 腾讯云服务器已完成 COS 基础配置，但不在数据库尚未验证时启用定时备份；
- 先部署 Docker Compose，确认 PostgreSQL 容器为 `healthy`、持久化数据卷已挂载、数据库可连接；
- 执行迁移和最小读写检查，重启 PostgreSQL 容器后再次验证数据仍在，确认持久化配置有效；
- 只有上述验收全部通过，才进入 COS 自动备份接入阶段。

### 5.2 每日 `pg_dump` → COS

- 定时任务每日对 PostgreSQL 执行 `pg_dump`，将带时间戳的备份文件上传到已配置的腾讯云 COS，本地临时文件在上传成功后清理；
- COS 密钥、Bucket、Region 和路径前缀仅通过服务器环境变量或受限配置文件提供，不进入仓库和容器镜像；
- 备份脚本必须在 `pg_dump` 失败、COS 上传失败或上传后对象校验失败时返回非零状态，不得将未上传成功记录为成功；
- 至少保留最近 7~14 天备份，并定期清理过期备份；
- 每月至少做一次恢复演练，验证可在新服务器或隔离恢复环境中恢复数据库并启动 API；
- 备份脚本记录开始时间、结束时间、文件大小、COS 对象路径和成功/失败状态，失败时通过日志或告警暴露；
- 备份使用独立 Compose profile 和 systemd timer，不随 Web/API 常规部署启动；专用 CAM 凭据仅拥有备份桶 `postgres/` 前缀的 `PutObject`、`HeadObject` 权限，14 天清理由 COS 生命周期规则执行。

### 5.3 其他运维要求

- API 提供健康检查接口，部署脚本执行容器状态、数据库连接和迁移检查；
- 使用 lockfile 固定 Node.js 依赖版本，生产部署前执行 `drizzle-kit` 迁移；
- Docker Compose、systemd、Nginx 和 PostgreSQL 的日志纳入统一检查范围；
- 记录服务器规格、磁盘使用率、内存使用率和导入期间资源峰值；达到资源阈值时暂停大批量导入并评估扩容；
- AI 用于生成部署脚本、分析日志和辅助升级，但生产变更仍需人工确认。

## 6. 迁移与回退

代码和数据按“服务层隔离、数据库标准化”设计：

```text
当前：浏览器 → Nginx（React/Vite + HTTPS）→ Hono.js/Node.js API → Drizzle ORM → PostgreSQL
扩容：浏览器 → Nginx 或静态托管 → Hono.js/Node.js API → Drizzle ORM → 托管 PostgreSQL
```

- API 层隔离数据库实现，前端不依赖数据库驱动或 ORM；
- 使用标准 PostgreSQL 类型、标准 SQL、UUID 和时间戳；
- 保留 `employee_work_batches`、`employee_work_items` 和 `app_users` 的稳定业务字段；店铺隔离（`shop_id`）与 RBAC 目录（角色/权限表）由数据库统一管理；
- 数据库迁移采用基线迁移策略：`0001_initial_baseline.sql` 为基线并面向空库执行，`0002`~`0013` 依次处理定价下线、工作室→店铺重构、台账 text 化、导入幂等、RBAC 目录、统计权限、SKU/订单唯一与编辑权限、客服员工工作导入权限、订单年月回填、尾程与利润回算、物流资费版本化及台账软删除；生产执行前先 `pg_dump` 备份；迁移执行器通过 advisory lock 保证并发安全；
- 如果服务器故障，先创建同规格或更高规格的新服务器，重新部署 Docker Compose，再从服务器外部备份恢复 PostgreSQL，最后切换 API 域名；
- v1 以每日备份为恢复边界，目标 RPO 不超过 24 小时；恢复时间通过新服务器恢复演练验证，不承诺单机故障期间持续可用；
- 如果数据规模增长，再将 PostgreSQL 迁移到腾讯云数据库，API 和前端接口保持稳定。

## 7. 风险与应对

| 风险 | 应对 |
|---|---|
| 单机故障 | PostgreSQL 验收后再启用每日 `pg_dump` → COS，准备新服务器恢复流程 |
| COS 上传或凭据异常 | 使用最小权限凭据，上传后校验对象，定时任务失败时保留日志并告警 |
| 磁盘或内存不足 | 限制单批 5 万行，监控磁盘和内存，清理日志并按需升级服务器配置 |
| 服务器入侵或密钥泄露 | 仅开放必要端口，SSH 使用密钥，密钥不进仓库，定期升级镜像 |
| 批量导入占满内存 | 服务端流式或分块处理，限制单批 5 万行，导入期间监控内存 |
| HTTPS 或域名配置失败 | 先用服务器 IP 做 API 健康检查，再绑定正式域名和证书 |
| 预算超出 | 先保持单机部署，不购买云数据库、负载均衡和 Kubernetes |
| 服务器维护复杂 | 使用 Docker Compose、systemd、自动备份、健康检查和 AI 辅助排障 |
| 需要更复杂权限或异步任务 | 增加队列或拆分 API 服务，不改变前端业务接口 |

## 8. v1 不做的技术投入

- 不使用 Kubernetes、服务网格和多机集群；
- 不提前购买云数据库、负载均衡和消息队列；
- 不让浏览器直接访问 PostgreSQL；
- 不让前端直接使用 Drizzle ORM 或数据库连接字符串；
- 不把数据库密码、JWT 密钥或备份凭据放入前端；
- 不在 v1 引入数据库级完整操作审计、修改历史和删除日志，仅保留 API 访问日志和台账导入排障日志；
- 只保留清晰的前端 services、Hono.js API 接口、Drizzle schema/迁移、标准 SQL 和备份流程。
