# 选品工具需求文档（v1.0）

## 1. 项目概述

| 项目 | 内容 |
|---|---|
| 项目名称 | 团队选品工具（sku-table） |
| 目标用户 | 电商小团队 3~5 人（选品员、客服/运营、负责人） |
| 核心价值 | 集中管理商品数据，可追溯"谁选的"，支持客服跟进备注 |
| 形态 | Web 应用（PC 浏览器为主），内部使用，非商业产品 |

## 2. 背景与问题

- 现状：商品数据散落在 Excel 文件里，靠微信/网盘传来传去，版本混乱。
- 痛点：
  1. 不知道某个商品是团队里谁选回来的；
  2. 客服/运营对商品的处理状态（已联系供应商、价格待核实等）没有地方记录；
  3. 多人同时维护同一份数据容易冲突、覆盖。
- 目标：一个"登录即可用"的网页工具，导入 Excel → 集中筛选/查看 → 在线改备注。

## 3. 用户角色与权限

采用基于工作室（studio）的 RBAC 权限模型：权限默认拒绝，账号通过"工作室成员 + 角色 + 用户级 allow/deny"获得权限；用户级 deny 优先于角色 allow；权限按工作室生效，JWT 只存用户 ID，权限由服务端按当前工作室实时计算。

| 角色 | 说明 | 预置权限 |
|---|---|---|
| owner（负责人） | 工作室所有者，负责工作室和成员管理 | 全部 18 个权限码 |
| selector（选品员） | 负责找品、导入 Excel | 查看/导入员工工作与选品定价、查看/导入商品、编辑内部备注 |
| operator（客服/运营） | 负责跟进商品 | 查看员工工作、选品定价和商品，编辑内部备注 |

权限矩阵（18 个权限码，按业务域分组；✓ 表示预置授予）：

| 权限码 | owner | selector | operator |
|---|---:|---:|---:|
| `studio.manage` | ✓ | — | — |
| `member.read` | ✓ | — | — |
| `member.manage` | ✓ | — | — |
| `employee_work.read` | ✓ | ✓ | ✓ |
| `employee_work.import` | ✓ | ✓ | — |
| `employee_work.delete` | ✓ | — | — |
| `employee_work.rollback` | ✓ | — | — |
| `pricing.read` | ✓ | ✓ | ✓ |
| `pricing.import` | ✓ | ✓ | — |
| `pricing.edit` | ✓ | — | — |
| `pricing.delete` | ✓ | — | — |
| `pricing.rollback` | ✓ | — | — |
| `product.read` | ✓ | ✓ | ✓ |
| `product.import` | ✓ | ✓ | — |
| `product.note.edit` | ✓ | ✓ | ✓ |
| `product.fields.edit` | ✓ | — | — |
| `product.delete` | ✓ | — | — |
| `product.rollback` | ✓ | — | — |

权限规则：

- 仅已开通的团队成员（`is_active = true`）可登录，权限按当前工作室计算；
- 拥有 `member.manage` 的成员可以注册新管理员账号并管理团队成员，新账号创建后立即启用；
- 员工工作与选品定价导入权限为 owner + selector；
- 删除、编辑原始字段、回滚等权限码已入库（`*.delete`、`*.fields.edit`、`*.rollback`），接口暂不开放；
- 用户级权限支持 allow / deny 覆盖角色权限，deny 优先；
- 最后一个 owner 不允许被删除或降权；
- v1.1 已纳入成员管理、商品库与内部备注编辑（见 4.6）。

## 4. 功能需求

### 4.1 用户认证（P0）

- 邮箱 + 密码登录；账号仅限已开通的团队成员使用；
- 管理员可在工作台注册管理员账号，注册只校验邮箱格式，不验证邮箱所有权；
- 登录状态保持（刷新不掉线）；
- 页面右上角展示当前登录用户邮箱；
- 未登录访问任何数据页时跳转到登录页。

### 4.2 员工每日工作导入（P0）

- 老板统一上传客服/员工提交的 `.xlsx` / `.xls` 文件；
- 上传时填写实际工作员工和工作日期，员工暂时不需要登录；
- Excel 固定字段为：`序号、货号、采集平台、采集商品名称、采集商品链接、采集规格、采集价格(CNY)`；
- 系统自动记录上传账号、上传时间、文件名和批次信息，Excel 不负责提供员工和工作日期；
- 导入过程显示进度（已写入 x / 共 y 行）；
- 单批 ≤ 5 万行（数据库层强制 0~50000），支持同一员工不同日期重复导入；
- 导入失败时提示失败范围，支持重试。

### 4.3 员工工作记录查看与筛选（P0）

- 工作明细分页展示（每页 100 条）；
- 按员工和工作日期筛选；
- 可按采集平台、货号和商品名称筛选（后续扩展）；
- 列表字段：员工、工作日期、货号、采集平台、采集商品名称、采集商品链接、采集规格、采集价格。

### 4.4 数据编辑（P0 / P1）

- 在线编辑"内部备注"并保存（P0，核心需求）；
- 编辑商品字段（货号、价格等）（权限码已入库，接口暂不开放）；
- 删除单条数据（权限码已入库，接口暂不开放）；
- 按导入批次批量删除 / 回滚（权限码已入库，接口暂不开放）。

### 4.5 导入追溯（P0）

- 每个员工工作批次必须包含员工姓名、工作日期、上传账号、文件名、行数和上传时间；
- 工作明细必须关联批次，不允许脱离批次写入；
- 上传账号从已验证登录令牌确定，不接受客户端伪造；
- 员工实体由 `employees` 表按工作室维护，`employee_work_batches.employee_id` 引用 `employees.id`，`employee_name` 保留导入快照；
- 批次表预留 `archived_at` / `archived_by` 归档字段，默认查询排除已归档批次。

### 4.6 v1.1 范围（成员管理、商品库、备注编辑）

- 工作室管理：`GET /api/studios` 列出工作室、`POST /api/studios` 新建工作室；
- 成员管理：`GET/POST /api/studios/:studioId/members` 查看/添加成员，`PATCH/DELETE /api/studios/:studioId/members/:userId` 调整角色或移除成员；
- 用户查询：`GET /api/users?activeOnly=true` 获取启用成员列表，供成员管理选择账号；
- 商品库：`POST /api/imports` 导入商品（记录状态、错误行、支持归档），`GET /api/products` 查看商品列表；
- 备注编辑：`PATCH /api/products/:id/internal-note` 编辑商品内部备注，供客服/运营跟进；
- 员工工作与选品定价接口按当前工作室隔离，导入权限为 owner + selector；
- 分页接口预留 cursor 参数，供后续大数据量翻页。

## 5. 非功能需求

| 维度 | 要求 |
|---|---|
| 数据规模 | 最多几十万行（按 50 万行设计），单条约 500 字节 |
| 并发 | 3~5 人同时在线操作 |
| 性能 | 列表翻页/筛选 < 1s；导入 5 万行 ≤ 2 分钟 |
| 可用性 | 国内访问稳定，工作日随时可用 |
| 成本 | 腾讯云轻量应用服务器约 20~50 元/月，整体月均 ≤ 50 元 |
| 安全 | 数据仅团队成员可见；上传人不可伪造 |
| 部署与资源 | 前端、API 和 PostgreSQL 共用一台腾讯云轻量应用服务器；单批导入不超过 5 万行，并监控 CPU、内存和磁盘空间 |
| 备份与恢复 | 先部署 Docker Compose 并确认 PostgreSQL 容器健康、数据库可连接，再接入每日 `pg_dump` → 腾讯云 COS 自动备份；至少保留 7~14 天，目标 RPO 不超过 24 小时；服务器故障时可在新服务器恢复业务 |
| 可维护性 | Docker Compose、自动备份和 AI 辅助维护，控制人工运维负担 |

## 6. 数据字典（数据库与 RBAC 重建后）

## 7. 验收标准

1. 已开通负责人可以登录，未登录无法访问数据页面；
2. 只有管理员可以注册管理员账号，注册账号立即启用且可登录；
3. 导入员工工作 Excel 后，批次包含员工、工作日期、上传人和上传时间，每行明细关联批次；
4. 员工工作记录可以按员工和工作日期筛选，翻页正常；
5. 选品定价数据每次导入都保留独立批次和历史明细；
6. 3 人同时使用无明显卡顿；
7. 5 万行导入可在 2 分钟内完成。
8. 生产环境先通过 Docker Compose 和 PostgreSQL 健康验收，再启用每日 `pg_dump` → COS 自动备份，并验证备份对象可下载和恢复。
9. 空库执行基线迁移 `0001_initial_baseline.sql` 成功，`schema_migrations` 只登记该基线，历史 0001~0006 不再存在；生产执行前先 `pg_dump`；
10. `pnpm db:seed` 可重复执行且幂等：角色/权限目录、owner 账号、默认工作室与成员关系不重复创建，缺省工作室名为"默认工作室"；
11. 权限矩阵与 RBAC 规则一致：owner 拥有全部权限，selector / operator 预置权限符合目录；用户级 deny 优先于角色 allow，默认拒绝；
12. 跨工作室隔离生效：业务根表按 `studio_id` 隔离，子表 `(batch_id, studio_id)` 组合外键阻止跨工作室关联；
13. 最后一个 owner 不允许被删除或降权；
14. 商品与成员接口可用：`GET /api/products`、`PATCH /api/products/:id/internal-note`、`GET /api/users?activeOnly=true`、工作室成员管理接口（增删改返回与权限一致）。

## 8. 非目标（v1 不做）

- 删除、编辑原始字段、批次回滚接口（权限码已入库，暂不开放接口）；
- 工作室内部的子权限矩阵自定义（预置角色固定，用户级 allow/deny 由接口后续开放）；
- 单工作室内的多店铺 / 多部门数据隔离；
- 数据看板、统计图表；
- 移动端 App；
- 微信登录 / 消息通知。

## 9. 架构约束

- v1 使用腾讯云轻量应用服务器，React/Vite 构建产物、Hono.js/Node.js API 和 PostgreSQL 通过 Docker Compose 部署；
- 前端通过 HTTPS 调用 Hono.js/Node.js API，浏览器不得直接连接 PostgreSQL；
- 所有数据库访问必须经过后端服务层封装，页面组件不得直接依赖数据库驱动；
- API 必须从已验证的登录令牌确定当前用户，`created_by` 不接受客户端传入；
- 业务数据关联自有 `app_users` 表，工作室隔离与 RBAC 由 `studios` / `studio_members` / 角色权限表统一管理，使用标准 PostgreSQL 类型、外键、索引和事务；
- PostgreSQL 不开放公网端口，数据库密码、JWT 密钥和备份凭据不得进入前端或代码仓库；
- React/Vite 构建产物、Hono.js API 和 PostgreSQL 均部署在同一台腾讯云轻量应用服务器；
- Nginx 提供前端静态文件、HTTPS 和 `/api` 反向代理，Hono.js API 与 PostgreSQL 只通过 Docker Compose 内部网络通信；
- Docker Compose 配置服务开机启动和异常重启；服务器防火墙只开放 80、443 及受限 SSH，PostgreSQL 端口不对公网开放；
- 服务器已完成 COS 基础配置；后续必须先部署 Docker Compose，确认 PostgreSQL 容器状态健康且数据库可连接，再启用每日 `pg_dump` → COS 定时备份；
- COS 备份至少保留 7~14 天，并定期执行恢复演练；v1 不承诺单机高可用；
- 后续如需迁移到云数据库或 BaaS，应保留现有业务表和 API 服务接口；
- v1 不引入 Kubernetes、消息队列、操作审计、修改历史和删除日志。
